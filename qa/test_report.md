## 3. รายการข้อบกพร่องและการแก้ไข (Bug List)

### BUG-001: Zod 4 อัปเกรดทำให้ `error.errors` เป็น undefined จนเซิร์ฟเวอร์แครช 500

- **ระดับความรุนแรง**: S1 (ฟังก์ชันตรวจสอบข้อมูลล้มเหลว ข้อผิดพลาดของผู้ใช้ถูกยกระดับเป็น 500 Internal Error)
- **สถานะ**: ได้รับการแก้ไขและตรวจซ้ำผ่านแล้ว (Closed)
- **รอบการตรวจซ้ำ**: 0
- **วิธีการตรวจพบ**: การทดสอบอัตโนมัติ (`qa/run_suite.mjs` รอบแรก)
- **ขั้นตอนการเกิดปัญหา**:
  1. เรียก API ที่มี Zod SafeParse Validation (เช่น `POST /api/tasks`)
  2. ส่ง Body ที่ไม่ถูกต้อง (เช่น `{ title: "" }`)
- **พฤติกรรมที่คาดหวัง**: ตอบกลับ HTTP 400 Bad Request พร้อมข้อความแจ้งเตือนข้อผิดพลาดที่ชัดเจน
- **พฤติกรรมจริง**: เกิด `TypeError: Cannot read properties of undefined (reading '0')` และเซิร์ฟเวอร์ส่งกลับ 500
- **หลักฐาน**: มี 9 เคสในการรันรอบแรกไม่ผ่านเนื่องจากได้รับ HTTP 500
- **สภาพแวดล้อม**: Node.js 22 + Nuxt 3.16 + Zod 4.4.3
- **การวิเคราะห์สาเหตุรากเหง้า (Root Cause)**: ใน Zod 4 อาเรย์ `.errors` ถูกเปลี่ยนชื่อเป็น `.issues` การเรียก `.errors[0]` จึงทำให้ระบบแครช
- **ไฟล์ที่ได้รับผลกระทบ**: ครอบคลุม API สร้าง/แก้ไขการ์ด, คอลัมน์, งานย่อย, คอมเมนต์, ป้ายกำกับ และการแจ้งเตือน
- **การแก้ไข**: อัปเดตโค้ดเป็น `parseResult.error.issues?.[0]?.message || parseResult.error.message` ในทุกไฟล์
- **การตรวจซ้ำ**: ตรวจสอบผ่านครบทุกเคสที่เกี่ยวข้อง

### BUG-002: ลำดับการตรวจสอบสิทธิ์ใน `kick.delete.ts` สลับตำแหน่ง

- **ระดับความรุนแรง**: S2 (ลำดับการตรวจสอบสิทธิ์และหลักความปลอดภัย)
- **สถานะ**: ได้รับการแก้ไขและตรวจซ้ำผ่านแล้ว (Closed)
- **รอบการตรวจซ้ำ**: 0
- **วิธีการตรวจพบ**: การทดสอบอัตโนมัติ (`TC-05-02`)
- **ขั้นตอนการเกิดปัญหา**:
  1. ล็อกอินด้วยสมาชิกทั่วไป (Member)
  2. ส่งคำสั่งลบเพื่อพยายามเตะ Owner ออกจากโปรเจกต์
- **พฤติกรรมที่คาดหวัง**: ผู้ใช้ไม่มีสิทธิ์บริหารจัดการ ควรถูกสกัดด้วย **403 Forbidden** ทันที
- **พฤติกรรมจริง**: ระบบไปชนเงื่อนไข "ห้ามเตะ Owner" ก่อน จึงส่งกลับ **400 Bad Request**
- **หลักฐาน**: เคส `TC-05-02` ตรวจพบ Assertion Error `400 !== 403`
- **สภาพแวดล้อม**: `server/api/members/kick.delete.ts`
- **การวิเคราะห์สาเหตุรากเหง้า (Root Cause)**: โค้ดตรวจสอบกฎห้ามเตะ Owner ถูกวางไว้ก่อนการตรวจสอบสิทธิ์ของผู้เรียก
- **การแก้ไข**: สลับให้การตรวจสอบสิทธิ์ผู้ดำเนินการขึ้นมาเป็นอันดับแรกสุด ปฏิบัติตามหลัก Defense-in-Depth
- **การตรวจซ้ำ**: ตรวจสอบผ่านในรอบ Regression Test
