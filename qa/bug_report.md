### BUG-001: การอัปเกรดเป็น Zod 4 ทำให้เกิด `TypeError` ส่งผลให้ระบบตอบกลับ HTTP 500 แทน 400

- **ระดับความรุนแรง (Severity)**: S1 (ระบบตรวจสอบข้อมูลล้มเหลว ข้อผิดพลาดของผู้ใช้ถูกยกขึ้นเป็น 500 Server Error)
- **สถานะ**: ได้รับการแก้ไขและตรวจซ้ำผ่านแล้ว (Closed)
- **รอบการตรวจซ้ำ**: 0 (ผ่านทันทีหลังแก้)
- **วิธีการตรวจพบ**: การทดสอบอัตโนมัติ (`qa/run_suite.mjs` รอบแรก)
- **ขั้นตอนการเกิดปัญหา (Reproduction Steps)**:
  1. ส่งรีเควสต์ด้วยบัญชีที่ผ่านการล็อกอินแล้ว
  2. ยิงไปยัง `POST /api/tasks` ด้วย Body ที่ไม่ถูกต้อง เช่น `{ title: "" }`
- **พฤติกรรมที่คาดหวัง**: ตอบกลับ HTTP 400 Bad Request พร้อมข้อความ `message: 'กรุณาระบุชื่องาน'`
- **พฤติกรรมจริงที่เกิดขึ้น**: เกิด `TypeError: Cannot read properties of undefined (reading '0')` และเซิร์ฟเวอร์ตอบกลับ 500
- **หลักฐาน (Evidence)**: สคริปต์ `qa/run_suite.mjs` รอบแรกล้มเหลว 9 เคสเนื่องจากเซิร์ฟเวอร์ตอบกลับ 500
- **สภาพแวดล้อม**: Node.js 22 + Nuxt 3.16 + Zod 4.4.3
- **การวิเคราะห์สาเหตุรากเหง้า (Root Cause Analysis)**:
  - **Root Cause**: Zod v4 มีการปรับโครงสร้างภายใน โดย `safeParse()` ในเวอร์ชันนี้จะไม่ส่งอาเรย์ `.errors` มาอีกต่อไป แต่เปลี่ยนไปใช้ฟิลด์ `.issues` แทน โค้ดเดิมที่เข้าถึง `parseResult.error.errors[0]` จึงเกิด JavaScript Null Pointer / Undefined Exception ทันที
  - **ตำแหน่งไฟล์**:
    - `server/api/tasks.post.ts:18`
    - `server/api/tasks.put.ts:18`
    - `server/api/columns/create.post.ts:14`
    - `server/api/columns/update.put.ts:14`
    - `server/api/notifications.put.ts:13`
    - `server/api/projects/labels.post.ts:14`
    - `server/api/tasks/comments.post.ts:13`
    - `server/api/tasks/subtasks.post.ts:13`
    - `server/api/tasks/subtasks.put.ts:14`
  - **ระดับความมั่นใจ (Evidence Level)**: E3 (สามารถทดสอบจำลองซ้ำได้อย่างแม่นยำ 100%)
- **ขอบเขตผลกระทบ 5 มิติ (Impact Dimensions)**:
  - **ฟังก์ชันการทำงาน**: การสร้าง/แก้ไขการ์ดงาน, คอลัมน์, งานย่อย, คอมเมนต์ และการแจ้งเตือน
  - **ข้อมูลในระบบ**: ไม่มีความเสียหายต่อฐานข้อมูล
  - **ผู้ใช้งาน**: ผู้ใช้จะเห็นข้อความ 500 แทนที่จะเห็นคำแนะนำกรอกแบบฟอร์มที่ถูกต้อง
  - **ความปลอดภัย**: เสี่ยงต่อการเปิดเผย Stack Trace ภายในเซิร์ฟเวอร์
  - **ความเสี่ยงจากการแก้ไข**: เป็นการแก้ไขตรรกะการดึงข้อความแจ้งเตือน ไม่กระทบกับฟังก์ชันการทำงานอื่น
- **เกณฑ์การให้ระดับ S1**: ข้อผิดพลาดระดับโครงสร้างที่ทำให้การแจ้งเตือนการกรอกข้อมูลกลายเป็นเซิร์ฟเวอร์ล่ม
- **แนวทางการแก้ไข**: ใช้โค้ดที่ปลอดภัย: `parseResult.error.issues?.[0]?.message || parseResult.error.message`
- **การตรวจซ้ำ (Regression)**: รันเคสที่เกี่ยวกับการตรวจสอบ Body ทั้งหมด (TC-01, TC-03, TC-04)

### BUG-002: ลำดับการตรวจสอบสิทธิ์ใน `kick.delete.ts` สลับตำแหน่ง

- **ระดับความรุนแรง (Severity)**: S2 (ลำดับการตรวจสอบความปลอดภัยและประสบการณ์ผู้ใช้)
- **สถานะ**: ได้รับการแก้ไขและตรวจซ้ำผ่านแล้ว (Closed)
- **รอบการตรวจซ้ำ**: 0 (ผ่านทันทีหลังแก้)
- **วิธีการตรวจพบ**: การทดสอบอัตโนมัติ (`TC-05-02`)
- **ขั้นตอนการเกิดปัญหา (Reproduction Steps)**:
  1. ล็อกอินด้วยสมาชิกทั่วไป (Member)
  2. ส่งคำสั่ง DELETE เพื่อเตะ Project Owner: `/api/members/kick?projectId=X&memberId=ownerId`
- **พฤติกรรมที่คาดหวัง**: เนื่องจากผู้ใช้ไม่มีสิทธิ์ `MANAGE_PROJECT` ระบบควรปฏิเสธด้วย **403 Forbidden** ทันที
- **พฤติกรรมจริงที่เกิดขึ้น**: ระบบไปชนกฎข้อห้ามเตะ Owner ก่อน จึงตอบกลับด้วย **400 Bad Request** ทำให้ผู้ใช้ที่ไม่มีสิทธิ์ล่วงรู้สถานะสมาชิกได้
- **หลักฐาน (Evidence)**: เคส `TC-05-02` ตรวจพบ Assertion Error `400 !== 403`
- **สภาพแวดล้อม**: `server/api/members/kick.delete.ts:34-71`
- **การวิเคราะห์สาเหตุรากเหง้า (Root Cause Analysis)**:
  - **Root Cause**: การวางโค้ดตรวจสอบ `project.ownerId === targetMember.userId` (400) ไว้ก่อน `isOwner || hasManagePermission` (403) ทำให้การตรวจสอบสิทธิ์ล่าช้ากว่าการตรวจสอบกฎธุรกิจ
  - **ตำแหน่งไฟล์**: `server/api/members/kick.delete.ts:35-48`
  - **ระดับความมั่นใจ (Evidence Level)**: E3 (โค้ดชัดเจนและตรวจจับได้จากการทดสอบ)
- **ขอบเขตผลกระทบ 5 มิติ (Impact Dimensions)**:
  - **ฟังก์ชันการทำงาน**: API จัดการการเตะสมาชิก
  - **ข้อมูลในระบบ**: ไม่มีการเจาะหรือขโมยข้อมูลเกิดขึ้น
  - **ผู้ใช้งาน**: ได้รับ HTTP Status Code ไม่ตรงตามมาตรฐานความปลอดภัย
  - **ความปลอดภัย**: ขัดกับหลัก Defense-in-Depth (ต้องตรวจสอบ Authorization ก่อนเสมอ)
  - **ความเสี่ยงจากการแก้ไข**: สลับลำดับ if-statement ไม่มีความเสี่ยงต่อส่วนอื่น
- **เกณฑ์การให้ระดับ S2**: ระบบเดิมยังคงป้องกันไม่ให้เตะ Owner ได้อยู่ เพียงแต่ลำดับและรหัสสถานะไม่ถูกต้อง
- **แนวทางการแก้ไข**: ย้ายการตรวจสอบสิทธิ์ของผู้เรียก (`isOwner || hasManagePermission`) ขึ้นมาเป็นด่านแรกสุด
- **การตรวจซ้ำ (Regression)**: รันเคส `TC-05-02` ซ้ำ
